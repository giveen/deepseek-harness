# Agent Note：SQLite Phase 3 保留标记与清扫

Status: implemented

[English](2026-08-19-sqlite-phase3-retention-mark-sweep.md) | 中文

## 问题

Phase 1 刻意保留了会话删除问题，因为直接删除可能在 fork、活跃会话、查询 projection、附件、导出物或其他客户端仍依赖数据时移除耐久历史。SQLite 后端现在需要有界保留能力，但不能把清理变成隐式后台任务，也不能删除无法证明所有权的工件。

## 决策

会话持久化服务提供提供方可选的 `markForDeletion(ids, reason?)`、`listDeletionMarks()` 和有界的 `sweepMarked(limit?)` 操作。继承的服务默认会明确拒绝这些操作，因此无法安全持久化删除状态的提供方不会静默声称支持保留清理。

SQLite 提供方将标记存放在 `session_deletion_marks` 表中，并将 schema version 从 `15` 提升到 `16`。标记操作是事务化且幂等的：不存在的 id、已有标记的 id 以及当前绑定活跃 `Session` 的 id 会被分别报告。标记会话从普通 `list`、snapshot、分页和 load-source 读取中排除，并拒绝新的 append。标记原因可选，最多 256 个字符。

清扫每次最多按确定的标记顺序处理请求的有界数量。只有在会话不活跃且没有实体化 child 使用未标记 `parent_session` 引用时，才会删除标记会话。SQLite 外键级联会在同一事务中删除会话的事件和删除标记。受保护的标记会保留到下一次清扫，结果会报告已删除、因活跃而保护、因引用而保护以及剩余数量。提交后，提供方会使每个已删除 id 的协调器状态失效，因此之后可以创建同 id 的新会话，而不会复用已删除的 cursor 或 preparation。

该操作只拥有 SQLite 会话行、事件行和删除标记，不会删除附件文件、查询索引行、导出物或其他 projection。收集这些数据需要各自明确的对账和所有权钩子。

## 考虑过的替代方案

**按 id 直接删除会话。** 拒绝：无条件删除会绕过活跃会话保护、fork 血统和运维可见的维护状态。

**创建标记时立即删除。** 拒绝：标记与清扫分离策略选择和有界破坏性工作，使运维能够检查标记，并为活跃或仍被引用的会话保留安全重试路径。

**即使存在未标记 child 也删除 marked parent。** 拒绝：child 持有指向 parent 的耐久血统引用；删除 parent 会留下无法解析的引用，并可能移除理解 fork 所需的历史。

**由会话提供方回收附件和 projection。** 拒绝：该提供方没有这些存储的权威枚举或所有权协议，删除其数据不安全。

**运行自动保留计时器。** 暂缓：调度、策略选择、跨进程协调和面向用户的可见性需要 Host 负责生命周期。当前实现是显式、有界 API，而不是无所有者的后台任务。

## 影响

SQLite 部署可以标记并清扫旧会话，而不执行无界删除事务，也不会让会话从维护界面中无声消失。标记会话会停止接收写入并从普通对账中消失，使删除意图可见，同时防止新的耐久工作与清扫竞态。Fork parent 可能一直保留标记，直到所有未标记 child 也被标记。

SQLite schema 会拒绝旧版或新版构建，而不是原地迁移。非 SQLite 持久化提供方保留现有会话数据，因为默认服务方法会失败，而不是假装支持删除。附件、projection、导出物、多进程和外部客户端的保留语义仍属于后续工作。

## 验证

SQLite 持久化测试覆盖幂等标记、不存在和活跃 id、标记会话可见性、child 引用保护、级联删除、有界清扫、原因校验及 schema version `16`。完成此变更后仍需通过仓库 typecheck、lint、package invariant、翻译配对、文档同步和聚焦 SQLite 测试。
