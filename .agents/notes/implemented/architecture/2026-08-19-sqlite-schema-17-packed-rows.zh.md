# Agent Note：SQLite schema 17 打包物理行

Status：已实现

[English](2026-08-19-sqlite-schema-17-packed-rows.md) | 中文

## 问题

SQLite 后端过去把每个逻辑会话事件单独存为 JSON 文本行。高频 assistant 分片因此反复承担行、JSON 和来源数据的开销，而逻辑会话约定并没有因此改变。物理重写必须降低这些开销，同时不能让存储标签进入会话消费者，也不能削弱崩溃恢复和保留语义。

## 决策

Schema 17 保持逻辑 `SessionEvent[]` 不变，只打包完全连续的 assistant 文本、推理和工具调用 delta。物理标签标识打包行；每行存储首个序列和时间、有限的共享 payload 数组以及时间差。每行最多表示 1,024 个逻辑事件和 1 MiB 未压缩 UTF-8 数据。带未知字段、surface 元数据、不兼容身份、缺口、不安全时间戳或可忽略标记的标量事件继续单独存储。

小于 4 KiB 的 payload 保持为 SQLite 文本。较大的 payload 使用 Zstandard level 3，但只有压缩 BLOB 小于原文时才采用。`sourceEventSeqs` 保持完整且有序，首项使用无符号 varint，后续项使用 ZigZag 有符号差值。解码会先校验字节数、序列、时间、字段和 varint 限制，再生成逻辑事件。

追加使用 `BEGIN IMMEDIATE`，在写锁内验证逻辑物理尾部，只打包新批次，绝不改写既有行。读取在协调器验证前展开打包行。后缀读取检查包含从打包行内部开始的请求所需的有限前驱范围。恢复会从物理首序列删除畸形物理尾部，并以事务方式插入合成 closer；已提交区域的物理损坏仍然报错。

本 fork 的 `session_deletion_marks` 表、列表过滤、活动会话保护、被 child 引用的 parent 保护、revision 跟踪、诊断、备份以及可配置 journal/checkpoint 设置都保留在 schema 17 中。既有 schema 版本会被拒绝；不会隐式迁移 schema 16。

## 备选方案

保留每个事件一行 JSON 文本被否决，因为高频分片仍会承担可避免的物理行和来源数据开销。每次追加都重写此前所有行被否决，因为它会增加 WAL 流量，并使崩溃恢复依赖不断增长的重写范围。自动迁移 schema 16 被否决，因为中断恢复、备份验证、磁盘空间要求和逻辑等价性需要由单独的迁移项目负责。通用压缩层被否决，因为 SQLite schema 必须自行拥有标签、限制和解码校验。

## 结果

长 assistant 流使用更少的物理行，同时保留精确的逻辑分片、时间戳、工具调用片段、来源和可忽略事件。直接读取 SQL 的消费者必须理解打包标签，或通过提供方读取。打包段会在持久批次边界处分割，因此压缩率会随批处理而变化。`DatabaseSync`、压缩和解压仍是同步操作，可能阻塞事件循环。

切换到此构建前，运维人员必须备份或导出 schema 16 数据库。提供方会对外部 schema、畸形打包行、陈旧追加尾部、无效来源数据和过大的打包数据 fail closed，而不是猜测恢复方式。

## 验证

Codec 和压缩测试覆盖打包、分割、Zstandard 选择、来源往返、存储标签冲突、畸形行和可删除尾部。差异集成覆盖将恢复的逻辑日志和后缀与追加输入比较，并检查物理打包行数量。现有 SQLite contract、保留、修复、备份和完整性测试仍然通过。
