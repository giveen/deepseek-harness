# Agent Note: Per-model image capability setting

Status: implemented

English | [中文](2026-08-19-per-model-image-capability.md)

## Problem

OpenAI 兼容的本地服务器可以提供视觉模型，却不一定会通过模型目录接口声明多模态能力。适配器会正确拒绝未声明 `image` 的模型所收到的图片消息，但模型页面没有让用户明确声明该能力的入口。

## Decision

pi-ai 模型编辑器在每个模型行的高级设置中提供**支持图片输入**复选框。启用时写入 `input: [text, image]`；关闭时写入 `input: [text]`。该设置适用于手动声明和本地 OpenAI 兼容路由，现有适配器能力检查保持不变。直接 DeepSeek 编辑器不提供该控件，因为该适配器仍然只支持纯文本。

关闭时写入明确的纯文本列表，而不是删除该字段。这样当路由之后获得 `[text, image]` 回退值时，模型级选择仍然具有优先级，同时保留既有的模型解析优先级和持久化设置格式。

## Consequences

- 本地 llama.cpp 兼容视觉模型可以在“设置 → 模型”中启用，无需手动编辑 `settings.yaml`。
- 声明仅作用于单个 pi-ai 模型，因此同一路由可以安全地同时提供纯文本模型和视觉模型。
- 系统不会验证端点是否真的支持该能力；错误声明仍可能被提供方拒绝。
- 除非已存储的 `input` 包含 `image`，或用户启用该控件，现有模型仍保持纯文本能力。

## Alternatives considered

**根据 `mmproj`、模型名称或本地服务器参数推断视觉能力。** 不采用，因为 Harness 不拥有服务器进程，也无法可靠识别 OpenAI 兼容端点实际选择的模型。

**为本地路由的所有模型启用图片输入。** 不采用，因为同一路由可以提供混合的纯文本模型和视觉模型，过度声明会让持久化的图片请求到达无法处理它的端点。

**要求直接编辑 `settings.yaml`。** 不采用，因为该能力会影响模型请求，而模型目录已经由设置界面管理；隐藏字段会让已有适配器契约难以发现。
